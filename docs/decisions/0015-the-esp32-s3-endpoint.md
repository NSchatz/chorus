# 0015: the ESP32-S3 endpoint, and every constant it fixed

- Status: decided
- BRIEF.md sections 5.2, 5.3 and 6; roadmap phase `chorus#EMBEDDED-5`
- Recorded by: EMBEDDED-5 (spec S0039-chorus-embedded-5)
- Evidence commit: `6af38bf4592b4187ad0a9f0a8a1dcd55c7fc6402`, the tree this
  phase started from. At that commit there is no `firmware/` tree, no C source,
  no ESP-IDF component, no `sdkconfig`, no pin map and no amplifier driver
  anywhere in the repository; the roadmap's evidence line for the phase is four
  words, "no firmware/ tree at the pin". There is also no eFuse or OTA code of
  any kind, so the scan this phase adds starts green and its value is that it
  stays green.

## What this decides

Not that there is a second endpoint - BRIEF.md decided that. This entry records
what the second endpoint IS: which pieces are shared with the Rust side and
how, what the amplifier bring-up order is and why that order rather than
another, every constant this phase fixed with what it was chosen from, and -
just as importantly - every constant it deliberately did NOT fix, written as
the literal word `unknown` in `firmware/config/endpoint.conf`.

Every number is committed once, in that file.
`firmware/tests/test_i2s.c` asserts the committed file breaks no rule and that
a smuggled value makes the checker go red; `firmware/Makefile` runs the checker
before it compiles anything, so a configuration that breaks a rule refuses
rather than builds.

## The link: nothing is asserted about it

This phase asserts NOTHING about which link the endpoint uses. Wi-Fi power
save, the modem-sleep default, the DTIM reception delay and every wireless
timing claim belong to `chorus#WIFI-7`, which asserts the power-save mode by
name and measures the jitter both with it and without it.

So `firmware/config/endpoint.conf` carries a server address and nothing about a
link, `firmware/src/session.c` opens a TCP connection through the ordinary BSD
socket API (which lwIP provides on the target unchanged), and
`firmware/sdkconfig.defaults` sets no Wi-Fi option at all and says in its own
comments which phase owns the ones it leaves alone. An endpoint on wire and an
endpoint on Wi-Fi are the same firmware here, and the difference between them
is a measurement WIFI-7 will take.

## The cores are mirrors, and the fixtures are what makes that true

The roadmap phase's scope note: "The sync and protocol cores arrive here as C
mirrors validated against FOUNDATION-1's fixtures, which is the whole reason
those fixtures are files."

**The protocol core** (`firmware/src/protocol.c`) is held to
`fixtures/protocol/` in both directions, byte for byte and field for field.
`firmware/tests/test_protocol.c` runs the same two assertions
`fixtures/README.md` names, on the same files, and adds the decoder-behaviour
ORDER `docs/protocol.md` makes normative: a truncated header and an
over-declared length consume nothing, an unassigned type is stepped over, a
short payload and a bad field cost one frame each.

It ENUMERATES that directory rather than carrying a list of type names, the way
`test_sync.c` enumerates `fixtures/sync`. A hardcoded list checked against its
own length is a tautology and would let the C side fall silently behind the
vectors, which is the one thing `fixtures/README.md` says these files exist to
prevent. Enumerating makes the coupling real in both directions: a committed
vector pair with no C mirror is red, and a mirrored type with no committed pair
is red. Both are demonstrated on a scratch copy of the fixture directory rather
than asserted, in the shape `test_scan.c` already uses.

**The sync core** (`firmware/src/sync_servo.c`, `sync_sim.c`, `sync_rng.c`,
`sync_scenario.c`) is held to two things. First, every scenario under
`fixtures/sync` drives the modelled playout error below that scenario's
declared bound by its declared deadline and holds it for the whole rest of the
run - the phase's own acceptance, run against the C core. Second, and this is
the assertion that makes the first one mean anything, it reproduces what the
Rust core did EXCHANGE BY EXCHANGE: the same round trip, the same raw estimate,
the same sample SELECTED out of the window, the same filtered offset, the same
servo tier and the same correction. Two implementations can converge for
different reasons and only one of those is a mirror.

That second assertion needed a file to be held to, so this phase adds
`fixtures/sync/crosscheck/`, one `.expected` per scenario, generated by
`make sync-vectors` and asserted byte-identical by
`crates/sync/tests/crosscheck_vectors.rs`. `crates/sync` gained a purely
additive `run_recorded` for it, with `run` delegating to it, so there is one
loop and not two: a recording path that had drifted from the graded one would
be a cross-check against something nothing runs.

**The comparison is exact, not approximate.** Doubles cross in the shortest
decimal that round-trips, so `strtod` on the C side recovers the identical bit
pattern, and the endpoint is compiled with `-ffp-contract=off -fno-fast-math`
so a fused multiply-add cannot round differently from the two operations the
Rust side compiles to. All 300 exchanges across the five committed scenarios
match exactly, including `02-wired-loaded`, whose exponential jitter draws go
through `log`.

### The reading taken on an unrecognised message type

`docs/protocol.md` says two readings are conformant: a reader whose transport
preserves message boundaries SKIPS an unassigned type using its length prefix,
and a reader on a stream transport is entitled to treat one as lost alignment
and stop. The Linux client takes the second, "for the reason that it is the
component holding a DAC".

**The endpoint takes the first.** AC-7 of this phase requires it in as many
words: "THE SYSTEM SHALL skip the frame and keep the session open rather than
fail it." What the document actually forbids is narrower than either reading -
"What is not conformant is stepping over an uncorroborated length and then
playing what follows" - so the endpoint skips, counts the skip in telemetry,
and drops the connection if the NEXT frame is rejected, which is what lost
alignment looks like from there. A skip followed by a clean frame is a newer
peer; a skip followed by rubbish is a lost boundary, and the endpoint stops
rather than plays.

## The amplifier: behaviour is asserted and no address is named

**Every register-level constant of the amplifier is an open question, and this
phase does not close it.** The roadmap records why: "TI's datasheet is
normative and is published as a PDF the pass could not extract text from", so
the phase "asserts behaviour and names no address".

`firmware/config/endpoint.conf` therefore declares the I2C address, the
device-id register, the fault register, the analog-gain register, the
state-control register, the healthy device-id value, the no-fault value and the
analog-gain code as the literal word `unknown`. `unknown` is not a placeholder
that defaults to something: `chorus_amp_bring_up` refuses, names the key, and
leaves the output stage in high impedance. There is not one register literal in
`firmware/src/amp.c`, and `firmware/check/endpoint_scan.c` fails the suite if a
hex literal ever appears there.

### The order, and why it is that order

```
1. high impedance          needs no register, so it is reachable before the
                           part is known to be there at all
2. gain ceiling            checked before the bus is touched, so a refusal is
                           provably before any write and before any clock
3. unknown registers       refused by name
4. device id read          a NACK, a timeout or a bus error ends it
5. fault read              anything but the configured clear value ends it
6. analog gain written     now known to be inside the ceiling
7. I2S clock applied       into a stage that has been dead since step 1
8. output enabled
```

Steps 4 and 5 are before step 8, which is the first half of AC-2. Step 1 is
before step 7, which is the second half, including the first clock change.

**The order is graded on what the hardware saw, not on what the driver says it
did.** `firmware/tests/fake_amp.c` is a simulated part, a simulated output
stage and a simulated I2S controller writing into one event log that the driver
has no way to reach, and the simulated stage powers up in an UNKNOWN state
rather than a safe one - so the first clock change has to be preceded by an
explicit high-impedance command or the test fails. The fake also records,
independently of the log's order, whether the stage was in high impedance at
each clock change.

### The analog gain ceiling: 0.0 dB, and it is a policy and not a datasheet
number

`amp_analog_gain_ceiling_db = 0.0`, measured in dB above the part's LOWEST
analog gain setting.

This was NOT read off a datasheet, and saying so is the point. An over-set
analog gain damages a loudspeaker rather than failing a test; the register map
is unread; and the lowest setting the part offers is the only value that is
safe without a measurement. Raising it is a deliberate act that wants a
measured speaker sensitivity behind it. The endpoint refuses to enable output
for any requested gain above the ceiling, names the request, the ceiling and
the file, and leaves the stage in high impedance -
`firmware/tests/test_amp.c` asserts all four, and asserts the refusal happens
with zero I2C transactions on the bus.

The requested gain, `amp_analog_gain_db`, is configuration too, so a file that
asks for more than its own ceiling is refused by
`chorus-endpoint-config-check` before anything compiles.

### A fault stops the audio

AC-5 asks that a fault be surfaced "rather than continue playing silently", and
task 7 of the spec leaves the choice between stopping audio and escalating to
the decision record. **The endpoint stops the audio.**

An amplifier reporting a fault - overcurrent, overtemperature, DC at the output
- while driving a real loudspeaker is exactly the case where continuing is what
damages a driver, and this repository's fail-safe rule is that the irreversible
thing is the one you refuse. So `chorus_amp_poll_fault` puts the output stage in
high impedance, THEN stops the I2S clock, and hands back a status with a name;
the order is the same one bring-up uses and for the same reason - stopping a
clock is a clock change, and `chorus/amp.h` step 7 promises that every clock
change is made into a dead output, not only the first. Every unwind in this tree
kills the output before it touches the clock. On the telemetry side,
`chorus_telemetry_record_amp` sets `audio=stopped-on-amp-fault` for EVERY
non-OK amplifier status, so there is no state of the telemetry struct that
reports a fault and `audio=running`.

An amplifier that stops ANSWERING mid-run is treated the same way, for the same
reason: a part that has gone quiet is not a part that is known to be healthy.

## I2S: the rate, the width, and the multiple

```
i2s_sample_rate_hz  = 48000     the rate the server cuts and the Linux client
                                plays (config/verification.conf). A rate
                                conversion on the endpoint would be a second
                                clock domain inside the thing whose whole job
                                is to have one.
i2s_slot_bit_width  = 24        the width that makes the MCLK rule below bite,
                                chosen here rather than discovered on a bench
i2s_mclk_multiple   = 384       divisible by three, and the value the carried
                                reference names
i2s_dma_frame_num   = 240       5 ms at 48 kHz, and divisible by three
i2s_dma_desc_num    = 6
```

The rule, in the carried ESP-IDF I2S reference's own words
(`sources/...api-reference-per-a2e5866a`, the `I2S_STD_CLK_DEFAULT_CONFIG`
note):

> Please set the mclk_multiple to I2S_MCLK_MULTIPLE_384 while using 24 bits
> data width Otherwise the sample rate might be imprecise since the BCLK
> division is not a integer

And on the buffers, from the same page:

> when the data width is 24-bit, the data buffer should be aligned with 3-byte
> ... Additionally, `i2s_chan_config_t::dma_frame_num`,
> `i2s_std_clk_config_t::mclk_multiple`, and the writing buffer size should be
> the multiple of `3`, otherwise the data on the line or the sample rate will
> be incorrect.

At these values MCLK is 18 432 000 Hz and BCLK is 2 304 000 Hz, so MCLK divides
into BCLK exactly eight times.

`firmware/src/i2s.c` enforces three separate rules with three separate names,
and `firmware/tests/test_i2s.c` decides every multiple ESP-IDF's own enum names
one way or the other rather than testing the rule at one point:

- `mclk-multiple-not-divisible-by-three` at a 24-bit slot width;
- `dma-frame-num-not-multiple-of-three` at a 24-bit slot width;
- `bclk-division-is-not-integral`, the general form the same page states first
  ("Normally, MCLK should be the multiple of `sample rate` and BCLK at the same
  time"). Every multiple in ESP-IDF's enum happens to satisfy this at every
  slot width, so the case that exercises it is a hand-typed multiple from
  outside that enum - which is exactly the configuration a typo produces.

**AC-3 is not closed by any of this.** The roadmap is explicit that the
assertion is "graded by measuring the produced sample rate, not by reading the
config: an MCLK multiple not divisible by three makes the rate imprecise, which
the servo then spends its whole budget fighting while looking healthy." A
configuration read back agrees with itself whatever the hardware does. What is
committed here is the half a host can check - the rule, enforced at build time
and again before a clock is started - and `tools/endpoint-rig-run.sh` is the
entry point for the other half, which refuses by name until somebody has the
hardware.

## The pin map, with every exclusion sourced

```
pin_i2s_mclk       = 16      pin_i2c_sda        = 8
pin_i2s_bclk       = 17      pin_i2c_scl        = 9
pin_i2s_ws         = 18      pin_amp_power_down = 21
pin_i2s_dout       = 15      board_octal_psram  = yes
```

Every one of these is outside every range the carried ESP-IDF GPIO reference
for ESP32-S3 reserves (`sources/...api-reference-per-3e2a4093`), and the
endpoint refuses to build with one that is not:

> **SPI0/1**: GPIO26 ~ GPIO32 are usually used for SPI flash and PSRAM and not
> recommended for other uses. When using Octal flash or Octal PSRAM or both,
> GPIO33 ~ GPIO37 are connected to SPIIO4 ~ SPIIO7 and SPIDQS. Therefore, on
> boards embedded with ESP32-S3R8 / ESP32-S3R8V chip, GPIO33 ~ GPIO37 are also
> not recommended for other uses.

> **USB-JTAG**: GPIO19 and GPIO20 are used by USB-JTAG by default. If they are
> reconfigured to operate as normal GPIOs, USB-JTAG functionality will be
> disabled.

> **Strapping pin**: GPIO0, GPIO3, GPIO45 and GPIO46 are strapping pins.

`board_octal_psram` is DECLARED rather than probed, because a pin map is
checked before an image exists. It is `yes`, which is the conservative reading:
it extends the reserved range to GPIO33 to GPIO37, so a map that would be legal
on a quad part is refused here. `firmware/sdkconfig.defaults` sets
`CONFIG_SPIRAM_MODE_OCT=y` to match, and `firmware/tests/test_i2s.c` asserts
GPIO35 is accepted when the board declares `no`, so the flag is doing work
rather than decorating.

Two signals on one pin is also refused (`gpio-assigned-twice`), because that is
the mistake a table of numbers makes easiest to write.

## DMA descriptors stay in internal RAM

The carried ESP-IDF external-RAM guide (`sources/...api-guides-extern-392eae88`)
is flat about it:

> DMA transaction descriptors cannot be placed in PSRAM.

`dma_descriptor_placement = internal`, refused at configuration time if it is
not, and - because a runtime flag is easy to satisfy and easy to bypass -
`firmware/check/endpoint_scan.c` additionally refuses ANY external-RAM
placement anywhere in the endpoint tree: `EXT_RAM_BSS_ATTR`,
`EXT_RAM_NOINIT_ATTR`, `EXT_RAM_ATTR`, `MALLOC_CAP_SPIRAM`, `SPIRAM_MALLOC`.

That is deliberately broader than the platform's own rule. The endpoint tree's
large buffers are DMA buffers, so a flat prohibition costs nothing today and
closes the case where a descriptor arrives in PSRAM through an allocator flag
rather than an attribute. A legitimate future PSRAM buffer is a deliberate
change to this rule, not a quiet attribute.

## The scans, and why they are a list

`firmware/endpoint-units.conf` enumerates the endpoint, in exactly the shape
`audio-path.conf` already uses on the Rust side and for exactly the reason
`docs/decisions/0011-the-audio-path-is-a-list.md` gives: "is this code on the
endpoint" cannot be answered by watching a process run.

Six rules, each with red demonstrations committed rather than described:

1. no settable wall-clock read (AC-16). The endpoint has ONE clock reader,
   `firmware/src/monotonic.c`, and every other unit takes the time it needs as
   an argument, which is what makes the rule cheap to state and hard to evade;
2. no eFuse write (AC-13). "Each eFuse is a one-bit field which can be
   programmed to 1 after which it cannot be reverted back to 0", so there is no
   recovery and no place for one in this phase;
3. no OTA activation (AC-13). `chorus#FLEET-10` owns OTA, and its evidence is a
   deliberately bad image shipped and reverted;
4. nothing placed in external RAM (AC-12);
5. no register literal in `firmware/src/amp.c`, which is the mechanical
   guarantee behind "names no address";
6. the list is complete: every `.c` and `.h` under `firmware/src`,
   `firmware/include` and `firmware/main` is listed or excluded with a reason.

`firmware/main` is scanned although it is compiled only by ESP-IDF, and for the
strongest reason there is: it is the one place in the tree where an OTA call or
an eFuse write would compile.

The scanner is textual, and that limit is worth stating as
`crates/audio-path/src/scan.rs` states its own: a call reached through a macro
it cannot see is not caught. What it does catch is every ordinary spelling and
every way of quietly moving one off the list.

## The session supervisor

One rule: every outage looks the same from the endpoint. A transport close and
a transport that broke are both a read returning zero, `stream_end` is what
tells them apart, and "the server or the network disappears and returns" covers
both. So the supervisor treats them identically - link down, backoff, connect
again, resume - and there is no retry budget to exhaust.

```
reconnect_first_backoff_ms = 100     most outages are a server restart
reconnect_max_backoff_ms   = 5000    a link down for an hour is not a busy loop
outage_minutes_seconds     = 130     what the graded outage-of-minutes run costs
```

`firmware/tests/session-outage.sh` grades this over a REAL loopback socket
against a REAL `chorus-server` process killed with SIGKILL and replaced, in
three shapes that fail differently:

- an outage shorter than one chunk. The chunk duration is a server option and
  that run uses the longest a 48 kHz stereo 16-bit stream can carry inside the
  protocol's 65535-byte payload, 320 ms, so a real process restart genuinely
  fits inside one chunk. The outage is MEASURED by the endpoint's own monotonic
  clock and compared against that duration. It measures about 100 ms here;
- an outage of minutes: 130 seconds of real wall clock against a real dead
  server. A modelled minute cannot exhaust a retry budget, which is the whole
  property being graded, so this run costs that much time every time
  `make firmware-check` runs. That cost is committed in `endpoint.conf` so
  changing it is a deliberate act;
- an outage long enough that several connect attempts are REFUSED before a new
  server process answers, so the connect-refused path runs and not only the
  peer-closed one.

## The toolchain: `espidf_version = v5.3`, and it is a pin

The carried references document the `driver/i2s_std.h` API, which exists from
ESP-IDF v5.0 onward. They carry no version marker of their own, so the exact
release whose pages were carried is an OPEN QUESTION and this value is a PIN
rather than a derivation. Its job is that `tools/firmware-image.sh` names it
when it refuses, and refuses a DIFFERENT installed toolchain against it: an
image built by a toolchain nobody chose looks exactly like an image that was.

The refusal comes before any output directory is created and before any object
is compiled, so there is nothing partial to leave behind. That ordering is the
assertion, not the message.

## What is NOT decided here

- **The register map.** Open question, declared `unknown`, refused by name.
- **The APLL as an I2S clock source.** The brief recommends it and neither
  Espressif page read documents one for this chip.
  `firmware/sdkconfig.defaults` takes `I2S_CLK_SRC_DEFAULT` and says nothing
  about APLL; settling it against the IDF version actually installed is work
  for the bench, and the MCLK rule above holds either way.
- **Anything wireless.** `chorus#WIFI-7`.
- **OTA, rollback, anti-rollback, Secure Boot, Flash Encryption.**
  `chorus#FLEET-10`, and the eFuse guardrail is not softened by any tier.
- **Zones, groups, volume, a control plane, mDNS.** `chorus#PRODUCT-6`.
- **DSP.** `chorus#DSP-8`. The endpoint plays what it is sent.
- **Whether AC-1 or AC-3 hold.** Neither is claimed anywhere in this
  repository. `docs/verification-record.md` says so and quotes the refusal.

## Known limitations

`firmware/main/app_main.c` and `firmware/main/esp_hal.c` are compiled only by
ESP-IDF and are NOT graded by anything that runs on a host. Everything they
bind is: the protocol core against committed vectors, the sync core against
committed scenarios and cross-check vectors, the bring-up ORDER against a
simulated part, the clock and pin rules at build time, the rejoin over a real
socket. What is left in those two files is the wiring, and the two criteria
that grade the wiring are the operator ones.

Nothing has been heard. A loudspeaker has not been connected to anything in
this repository, and the endpoint has never driven a pin.
