## What was run

A line-in (ADR 0066) on a wired endpoint plays in its own room at the local latency L_local. At the join time the server learns a second room has joined the group and asks the plan for the group latency L_group. The plan time-stretches the source (plays it slightly slower, by a raised-cosine ramp of the rate, a hold at the bound, and the mirror ramp) so the stamp offset (play-at minus capture instant) grows to L_group while every output chunk stays contiguous on the server timeline. The joining room is sent every chunk from the join and starts with the first that arrives in time at a latency its tier can start at. In the wired scenario the room later leaves and the plan shrinks the latency back by the same mechanism, the rate reversed.

Chunks travel as the house simulation's links model them (`config/sim-house/`, ADR 0048): the capture endpoint's forward path up, each player's return path down, base delay plus that link's jitter model, delivered in order. The server renders an output chunk once every source frame its cubic interpolator reads has arrived. The source signal is the frame index itself, and cubic (Catmull-Rom) interpolation reproduces a straight line exactly, so every sample the playing room hears is the source position it played: the criterion below is checked on the rendered audio, frame by frame. Inter-room error is the difference of the two endpoints' playout errors from the house simulation's own single-client runs, sampled at each chunk's play-at instant; both rooms render the same stamps, so the stamps add nothing to it by construction.

## The glitch criterion

For the room already playing, over the whole run: **(a)** output samples, read as source positions, strictly increase with every per-frame step inside [1 - r_max, 1 + r_max], and no frame is inserted (a stamp gap, heard as silence) or dropped (a stamp overlap); **(b)** no underrun: every chunk reaches it at least the endpoint guard before its play-at stamp; **(c)** the stamp offset never moves away from where the plan is heading, and every transition reaches its target; **(d)** the rate's change from one chunk to the next is inside the profile's slope bound r_max pi / (2 R) per frame times a chunk. For the pair once both play: |inter-room error| under BRIEF.md section 2.2's "Multiroom music, different rooms" acceptable bound (5 ms). The same checks run on the negative control, the latency set to L_group at once, which has to fail them.

## The rate bound

r_max = 500 ppm = 0.050 % = 0.865 cents. The cited threshold: the smallest mean frequency difference limen trained listeners showed for steady pure tones, 0.2 % (3.46 cents) at 1 kHz (Dai and Micheyl 2011, "Psychometric functions for pure-tone frequency discrimination", JASA 130(1), https://pmc.ncbi.nlm.nih.gov/articles/PMC3155586/, read 2026-10-01). r_max is a quarter of it; added to the endpoint servo's largest correction (300 ppm, `config/sync.conf`) it is 1.384 cents, still under half. The threshold is for two steady tones compared side by side, which is harder on the stretch than a slow glide inside music; the margin is a choice (ASSUMED until a listening test). Ramp R = 10 s (ASSUMED). A change of dL takes dL / r_max + R: 210 s per 100 ms of latency.

## What this does not show

- That nobody hears it. The bound is a cited threshold with a margin, not a listening test; the cubic interpolator's own artifacts are not modelled at all (the source here is a straight line).
- That a Wi-Fi room can start soon. It waits for the latency to reach its tier's floor, minutes at this bound (the scenario's table says how long); the decision record lists the options.
- Capture-clock drift against the server timeline, gaps in the source (an overrun on the capture device) and a join in the middle of a transition (the plan holds a new target until the running transition ends): the decision record's follow-ups.
- Anything on a real network, endpoint or DAC.
