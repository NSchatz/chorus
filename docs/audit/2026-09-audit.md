- Audited tree: `origin/main` at `4ecc782` (the goal-start tree `4b8433a` plus the goal-1 ledger;
  no product file differs). Line numbers are in that tree.
- Method (K20, program brief §5 item 2): a cold, adversarial audit by two agents that did not write
  the code, each assuming every claim in the code and its docs false until the code or a command
  showed otherwise. Auditor A took FOUNDATION-1, RIG-3, SYNC-4, EMBEDDED-5, WIFI-7 and guardrails

- Ranks: **HIGH** breaks a §3.1 guardrail, makes a stated success claim false, stops the product

  misleading claim, a test that cannot fail or a gap that will bite soon; **LOW** is hygiene or
  staleness.
- Who fixes what (I17): goal 2 fixes every HIGH finding and every cheap MED one; every other finding

  goal 2's report.

## Phase FOUNDATION-1 (Foundation)

**Success looks like (BRIEF §8):** "servo logic converging in simulation under realistic jitter and skew models before any hardware exists."
**Verdict:** met (in simulation), with model gaps
Rust (`crates/sync/tests/simulator_regression.rs:15-19`, `crates/sync/src/crosscheck.rs:38`) and C
(`firmware/tests/test_sync.c:48-68`) both discover `fixtures/sync/*.cfg` and the committed
`fixtures/sync/crosscheck/*.expected`; the C side asserts exchange-by-exchange equality with the
Rust record (`test_sync.c:302-347`), and the protocol vectors are read by both
(`crates/protocol/tests/common/mod.rs:18`, `firmware/tests/test_protocol.c:280-282`). So the
"same fixtures" claim holds. Five scenarios settle under a 1 ms bound and a neutered-servo control
fails (`crates/sync/src/sim.rs:257-285`), so the convergence test can fail. What "realistic" covers
is narrow: jitter is i.i.d. uniform or exponential only (`crates/sync/src/jitter.rs:21-35`), the two
directions share one distribution (`sim.rs:155-156`), and ADR-0006 lists no DAC delay, no loss, no
reordering (`docs/decisions/0006-sync-simulator-and-servo.md:164`).

### A-1 [MED] The simulator never models an asymmetric path, a heavy-tailed (Wi-Fi-like) link, or a drifting crystal, so "realistic jitter" is two i.i.d. symmetric distributions
- Where: `crates/sync/src/jitter.rs:21-35`, `crates/sync/src/sim.rs:153-156`, `crates/sync/src/config.rs:15` (constant-rate clock), `docs/decisions/0006-sync-simulator-and-servo.md:151-166`
- Evidence: `JitterModel` has only `Uniform` and `Exponential` (plus `none`); `forward_ns` and `return_ns` are both `base_delay_ns + config.jitter.sample_ns(&mut rng)`, so the mean path is always symmetric and the NTP offset estimate is unbiased by construction. `rg -n "asymmetr|wander|burst" crates/sync/src` returns nothing. The five `.cfg` files cap jitter at 200 us uniform or 150 us exponential mean.
- Why it matters: the offset error mode that dominates real LANs and all Wi-Fi (queueing asymmetry, bursts of tens of ms, temperature drift) is invisible to CI, so a servo regression there cannot fail any test; WIFI-7's looser bound has no simulator scenario at all.
- Proposed fix: add an asymmetric base delay, a bursty/heavy-tailed model and a slow ppm random walk to `SimConfig` and the C mirror, plus one scenario each with regenerated crosscheck vectors; suggested goal: 7.

### A-2 [LOW] The steady-state rate correction in three scenarios is 20 to 35 ppm away from the true skew, and no test looks at it
- Where: `fixtures/sync/crosscheck/02-wired-loaded.expected` (final_correction_ppm), `fixtures/sync/crosscheck/03-worst-case-skew.expected`, `fixtures/sync/02-wired-loaded.cfg`, `fixtures/sync/03-worst-case-skew.cfg`
- Evidence: wired-loaded has server -12.5 ppm and client +38 ppm (relative 50.5 ppm) and ends at `final_correction_ppm = -71.71589196998595`; worst-case-skew has a 100 ppm relative skew and ends at `65.4362402114487`. The regression asserts only the error bound and determinism (`crates/sync/tests/simulator_regression.rs:61-223`).
- Why it matters: the loop is holding the bound by limit-cycling on the rate rather than locking it, which on hardware is audible as a steady insert/drop rate far above the drift; nothing would notice if it got worse short of the 1 ms bound.
- Proposed fix: assert a steady-state rate error (mean correction over the back half vs `-(client_ppm - server_ppm)`) with a documented tolerance; suggested goal: 7.

## Phase SOUND-2 (First sound)

**Success looks like (BRIEF §8):** "Minimal server (FIFO in, chunks out) and a minimal Linux client
playing timestamped PCM via ALSA, no servo yet. Success: clean audio, plausible reported DAC delay,
stable buffer."

**Verdict:** code written, unproven on hardware

The server (`crates/server`, `crates/audio`), the client (`crates/client-linux`) and a `dlopen`
ALSA binding (`crates/alsa/src/lib.rs:15`, `:74`, `:278`) exist, and the baseline suite passes on
rust 1.98.0 (`baseline/ci/summary.txt`: build rc=0 44.5 s, playout rc=0 77.2 s). Every criterion that
rests on a device that reports a delay is NOT PASSED: the record's own machine had no `/dev/snd`
(`docs/verification-record.md:1037-1047`), the only device runs used ALSA `null`, which reports
`delay_us=0` for ever (`docs/verification-record.md:1071-1076`), and `docs/measurements/` holds no
`ten-minute-run.log`. So none of "clean audio", "plausible reported DAC delay" or "stable buffer" has
evidence; the buffer's stability is shown only against the modelled sink
(`docs/verification-record.md:1058`). `docs/sound-2.md:37-39` itself says the phase is not delivered.
The "FIFO in" half is only incidentally supported (B-2).

### B-1 [MED] README states first sound as a present fact; nothing has been heard
- Where: `README.md:26-27`; contradicted by `README.md:84`, `docs/sound-2.md:37-39`,
  `docs/verification-record.md:1043-1047`
- Evidence: `README.md:26-27`: "PCM goes in one end and comes out of a speaker at the other". The
  verification record for the same phase: "nothing that needs a device that paces, a real-time
  ceiling, or a device that can be pulled out mid-run ran, and none of it is claimed". `ls
  docs/measurements/` lists no ten-minute run log.
- Why it matters: the repo's front page makes the one SOUND-2 claim the evidence does not support;
  a reader cannot tell the phase is unproven without reading 1,243 lines of record.
- Proposed fix: reword to "is built to", and add a one-line status per phase (met / code written,
  unproven on hardware / partial / not started) to the README; suggested goal: 2.

### B-2 [MED] "FIFO in" is a plain file open: a writer that closes ends every client's stream, and no test uses a FIFO
- Where: `crates/server/src/source.rs:37-49`, `:143-150`; `crates/server/src/main.rs:667-742`
- Evidence: `source::open` treats any non-`tone` source as `FileSource::open(path)` (`File::open`),
  and `read` is a bare `self.file.read(buf)`; `Ok(0)` is the end of the stream (`source.rs:24`). On a
  FIFO, `read` returns 0 as soon as the producer closes, so the server emits `stream_end`, clients
  leave, and the next stream only starts when a NEW client arrives (`main.rs:733-740`: "Discarding
  them is what makes the next pass wait for a NEW listener"). The source is opened only after a client
  attaches (`main.rs:675-683`), so a FIFO with no writer blocks the supervisor inside `open`.
  `git grep -n 'mkfifo\|named pipe'` over the tree prints nothing: no test or tool exercises a FIFO.
- Why it matters: BRIEF §2.1 and §8 name a FIFO as the PCM source; a player that pauses or changes
  track (closing the pipe) tears down every endpoint's session instead of producing silence on a
  continuous timeline.
- Proposed fix: a `fifo:` source that holds the pipe open (`O_RDWR` or reopen on EOF), fills silence
  on underrun at the chunk cadence and never ends the stream on writer close; a test that writes,
  closes and re-opens a real `mkfifo` pipe; suggested goal: 7.

### B-3 [LOW] `docs/sound-2.md` grades itself against an outcome that is not BRIEF §8's
- Where: `docs/sound-2.md:24-27`
- Evidence: "The roadmap's SOUND-2 outcome has two halves: 'A Linux client plays a
  server-timestamped PCM stream through real speakers with a stable buffer', **and** 'the server
  earns its place on the household's production host'". BRIEF §8 item 2 says "clean audio,
  plausible reported DAC delay, stable buffer"; the quoted text comes from the umbrella roadmap.
- Why it matters: CLAUDE.md says a spec inherits the phase's acceptance from BRIEF; a second,
  paraphrased target lets the two drift.
- Proposed fix: quote BRIEF §8 verbatim and link the umbrella wording as secondary; suggested goal: 4.

## Phase RIG-3 (Measurement rig)

**Success looks like (BRIEF §8):** "the rig produces trustworthy numbers; drift matches crystal expectations."
**Verdict:** code written, unproven on hardware (and the device path is defective)
The analysis half is real and fixture-validated: sliding-window cross-correlation with sinc
reconstruction recovers a 254.0 us fixture delay to 0.039 us (`docs/decisions/0013-the-measurement-rig.md:69-80`),
and the free-run OLS fit recovers a fixture rate. Every file in `docs/measurements/` that carries a
timing figure labels itself a fixture (`rig3-free-run-noiseless-fixture.md`, `rig3-lag-fixture-reference-capture.md`,
`rig3-jitter-wireless-ps-*.md` say "THIS SERIES IS A COMMITTED FIXTURE AND NOT A MEASUREMENT"), so
nothing there is passed off as hardware. But the device-backed capture cannot capture what it
claims, and nothing produces a free-run series from two real clients.

### A-3 [HIGH] The capture tool plays its chirp to completion and only then starts recording, and it plays it on a local device rather than through the endpoints
- Where: `crates/measure/src/bin/chorus-measure-capture.rs:219-226`, `crates/measure/src/capture.rs:122-135`, `tools/measure/capture-run.sh:1-9,35-41`
- Evidence: `run()` calls `capture::emit(playback_device, ...)`, whose body ends `pcm.write(&raw)?; pcm.drain()?;`, and only after it returns calls `capture::record(capture_device, rate_hz, frames)`. The comment at `:219-223` says "The emitter runs first and drains, so the recording that follows carries the chirp", which is backwards: after `drain()` the chirp has finished. `playback_device` defaults to `CHORUS_CLIENT_DEVICE` (`:185-186`), a local ALSA device, and `capture-run.sh` starts no server and no endpoint. `rg -n -i chirp crates/server` finds nothing: no path puts a chirp into the grouped stream.
- Why it matters: every hardware criterion of RIG-3, SYNC-4 (`tools/sync-hour-run.sh:145`), EMBEDDED-5 (`tools/endpoint-rig-run.sh:150-158`) and WIFI-7 (`tools/wireless-characterization-run.sh:165`) goes through this binary, so on a real bench each would record silence or unrelated audio and refuse or report nothing; the verification record's "only hardware is missing" is false.
- Proposed fix: record and emit concurrently (capture thread started first, then emit), and add a server source that injects the configured chirp into the grouped stream (a `--source chirp` or a WAV/FIFO fixture) so the capture sees two endpoints playing the same chirp; add a loopback test against an ALSA `null`/`plug` pair if alsa-lib is provisioned; suggested goal: 2 (the ordering), 7 (the chirp source).

### A-4 [MED] No tool produces a free-run offset series from two real clients, so the free-run baseline can only ever be a fixture
- Where: `crates/measure/src/freerun.rs:355-366`, `crates/measure/src/fixtures.rs:422-432`, `crates/client-linux/src/delaylog.rs` (no offsets output), `docs/measurements/free-run-baseline.conf:15`
- Evidence: `rg -n "\[observations\]" --glob '!fixtures/**' .` matches only the fixture generator (`fixtures.rs:432`) and the reader; `rg -n "offsets" crates/client-linux/src` returns nothing; `rg -n -i "free.run|correction.*disabl" crates/client-linux/src` returns nothing, so there is no "correction disabled" client mode either.
- Why it matters: BRIEF §8 RIG-3 asks for "a free-run drift baseline between two clients"; the pipeline to get one does not exist even with hardware present.
- Proposed fix: a client flag that disables the servo and writes `t_ns offset_ns` observations in the `.offsets` format, plus a tool that pairs two clients' series; suggested goal: 7.

### A-5 [MED] `chorus-measure free-run` defaults to `--source fixture` and always overwrites `docs/measurements/free-run-baseline.conf`
- Where: `crates/measure/src/bin/chorus-measure.rs:210`, `crates/measure/src/bin/chorus-measure.rs:259-272`, `docs/measurements/free-run-baseline.conf:4`
- Evidence: `let source = options.value("source").unwrap_or("fixture")`; the baseline path defaults to `out.join(BASELINE_FILE)` and is written unconditionally. The conf's own header says "It is a MEASUREMENT, not a target" while its body is `source = fixture`.
- Why it matters: a hardware run without the flag is recorded as a fixture, and any later fixture run silently replaces a hardware baseline that other reports cite.
- Proposed fix: make `--source` required, refuse to overwrite a `source = hardware` baseline with a fixture one, and reword the header; suggested goal: 2.

### A-6 [MED] Saved reports cite "Build measured" commits that do not exist in the repository and were taken from dirty trees
- Where: `docs/measurements/rig3-free-run-noiseless-fixture.md:4`, `docs/measurements/rig3-lag-fixture-reference-capture.md:4-5`, `docs/measurements/rig3-jitter-wireless-ps-none.md:4-5`, `docs/measurements/rig3-jitter-wireless-ps-min-modem.md:4-5`, `docs/measurements/free-run-baseline.conf:20`
- Evidence: `git cat-file -t 60b639b98586ed9e1d0bf0c195870a2bf95a1172` and `... 9233f2fa9cb5494babd0561017c984ff74149d8c` both print `fatal: git cat-file: could not get object info`; the wireless reports say the tree "carried 22 uncommitted path(s)" and "23 uncommitted path(s)".
- Why it matters: the provenance line that makes a report reproducible points at nothing (squash-merge discarded it); the same will happen to the first real hardware report.
- Proposed fix: regenerate the fixture reports on a merged commit; have `report::build_identity` refuse a dirty tree for `source = hardware` and record the merge commit after landing; suggested goal: 4.

## Phase SYNC-4 (Synchronization)

**Success looks like (BRIEF §8):** "sustained sub-millisecond error, zero hard resyncs at steady state."
**Verdict:** code written, unproven on hardware
`crates/client-linux/src/sync.rs` closes the loop on `snd_pcm_delay` (`sync.rs:12`), filters
min-RTT, applies a PI rate law as sample insert/drop, and steps under a mute (`sync.rs:529-537`,
`633-665`). ADR-0014 publishes modelled-hour figures and labels them "a MODELLED result and is not
a measurement" (`docs/decisions/0014-the-sync-loop-on-the-real-path.md:143-146`). No sub-ms claim
is presented as measured: `README.md:5` states it as a target. The hour run that would grade the
phase cannot produce a number (A-7, and A-3).

### A-7 [HIGH] The SYNC-4 hour run streams a 440 Hz sine that the lag analyser is built to refuse
- Where: `tools/sync-hour-run.sh:74-77`, `crates/server/src/source.rs:59,87,146`, `crates/measure/src/lag.rs:169-173,243-252`, `config/measure.conf:30-31,59`
- Evidence: the script starts `chorus-server ... --source tone`; the tone is `(0.2 * (2.0 * PI * 440.0 * t).sin())`. The analyser refuses with `NoChirpPresent` unless at least `chirp_band_fraction_floor = 0.5` of a channel's energy lies in `chirp_start_hz = 1000` to `chirp_end_hz = 8000`. A 440 Hz tone has essentially none there.
- Why it matters: the one run that decides the make-or-break phase would end in `no-chirp-present` on a fully equipped bench.
- Proposed fix: stream the rig's chirp (the source in A-3) in `sync-hour-run.sh`, `endpoint-rig-run.sh` and `wireless-characterization-run.sh`, and add a CI test that feeds a server-generated stream through `lag::analyse` (via the fixture path) so the pairing cannot drift again; suggested goal: 2.

### A-8 [LOW] ADR-0014 says its modelled scenarios match the committed simulator fixtures; the worst-crystal-pair row does not
- Where: `docs/decisions/0014-the-sync-loop-on-the-real-path.md:148-155`, `crates/client-linux/tests/sync_loop.rs:507-511`, `fixtures/sync/03-worst-case-skew.cfg`
- Evidence: ADR row: "worst crystal pair | +50 and -50 ppm | 250 us base, exponential 150 us mean"; the fixture is `jitter_model = uniform`, `jitter_scale_us = 200.0`.
- Why it matters: small, but it is exactly the kind of drift between prose and fixtures the project says it prevents.
- Proposed fix: have the modelled-hour tests load the `.cfg` files instead of restating them; suggested goal: 2.

## Phase EMBEDDED-5 (Embedded bring-up)

**Success looks like (BRIEF §8):** "the embedded endpoint syncs comparably to Linux and survives disconnect/reconnect abuse unattended."
**Verdict:** partial (host-built cores only; the target image does not compile and plays nothing)
Host-built C cores (protocol, sync mirror, amp sequencer, session supervisor with backoff) pass
`make firmware-check`. The ESP-IDF image fails on `firmware/src/sync_sim.c:47`
(`static int finite(double)` clashes with newlib's `finite`) and `firmware/src/monotonic.c:16`
(`vTaskDelay`/`pdMS_TO_TICKS` with no `freertos/FreeRTOS.h` include; only `esp_timer.h` at `:5`),
per program brief §0.11. Beyond the compile errors, the target has no playout, no servo and no
reachable server.

### L-1 [HIGH] The ESP-IDF image does not compile for esp32s3: two source files fail
- Where: `firmware/src/sync_sim.c:47`, `firmware/src/monotonic.c:5`, `firmware/src/monotonic.c:16`
- Evidence: the goal-1 baseline (ESP-IDF v5.3.6 at `/cache/esp`, `IDF_PY_BUILD_JOBS=2`, cold build
  dir): `idf.py set-target esp32s3` rc=0 in 9.4 s; `idf.py build` rc=2 in 100.8 s, stopped at step
  1011 of 1044; `ninja -k 0 -j2` rc=1 lists exactly two failed objects, `src/sync_sim.c.obj` and
  `src/monotonic.c.obj`, with three errors:
  `firmware/src/sync_sim.c:47:12: error: static declaration of 'finite' follows non-static declaration`,
  `firmware/src/monotonic.c:16:5: error: implicit declaration of function 'vTaskDelay'` and
  `firmware/src/monotonic.c:16:16: error: implicit declaration of function 'pdMS_TO_TICKS'`.
  Newlib's `math.h` declares the BSD `finite()`, which the host build's strict C11 hides; the
  `CHORUS_TARGET_ESP32S3` branch of `monotonic.c` includes only `esp_timer.h`. `firmware/main/`
  (`app_main.c`, `esp_hal.c`) compiles clean under `-Werror`; the link step is not reached.
- Why it matters: EMBEDDED-5's endpoint has never been built as an image, so nothing about it can
  be flashed, sized or measured, and no check keeps it building (the gate compiles only the host
  cores).
- Proposed fix: rename the static helper in `sync_sim.c` (for example `chorus_finite`) and include
  `freertos/FreeRTOS.h` and `freertos/task.h` in the target branch of `monotonic.c`; then put the
  ESP-IDF compile (and link) for every approved target in `make gate` through ccache and a
  persistent build directory (K51, §4.2); suggested goal: 2.

### A-9 [HIGH] The firmware session counts audio chunks as "played" and discards them; no servo runs on the endpoint
- Where: `firmware/src/session.c:270-281`, `firmware/main/esp_hal.c` (no `i2s_channel_write`), `firmware/main/app_main.c:43-47,171-213`
- Evidence: on `CHORUS_MSG_AUDIO_CHUNK` the session does `state.telemetry.chunks_played++; state.telemetry.frames_played += ... audio_data_len / frame_bytes;` and nothing else. `rg -n "servo|i2s" firmware/src/session.c` matches only those chunk lines; the time-sync branch (`:282-300`) feeds `chorus_offset_filter_push` and never calls the servo. `rg -n i2s_channel_write firmware` returns nothing. `app_main.c` itself says "the session supervisor touches a socket and a filter and no hardware at all".
- Why it matters: telemetry that reports `frames_played` for audio that never left the chip is a false claim on the wire, and "sync core ported" (EMBEDDED-5) is not true: only the offset filter is ported into the running path.
- Proposed fix: add a jitter buffer and an I2S writer task (DMA from internal RAM), wire `chorus_servo_update` and frame insert/drop into it, and rename the counter to `frames_received` until then; suggested goal: 8.

### A-10 [HIGH] The committed endpoint configuration stops the board before the network: the amp map is `unknown`, the Wi-Fi credentials are `unknown`, and the server is loopback

### B-4 [MED] The control channel's 16 KiB request bound does not hold: one LAN peer can grow a line without limit, and a trickle holds a worker for ever
- Where: `crates/server/src/control.rs:60-65`, `:459-476`, `:545`; `crates/hostctl/src/lib.rs:69-70`,
  `:412`
- Evidence: the doc comment at `control.rs:62-64` says the bound "is what stops a peer that opens a
  connection and never stops typing from being an allocation". But the request line is read with an
  unbounded `reader.read_line(&mut line)` (`:461`) before any size check, and each header line is
  read in full by `read_line` (`:471`) before `read > MAX_REQUEST_BYTES` is tested (`:473`). A peer
  that sends bytes with no `\n` grows `line` until allocation fails. The server locks memory with
  `mlockall(MCL_CURRENT | MCL_FUTURE)` (`hostctl/src/lib.rs:69-70`, `:412`) under a 64 MiB
  `memlock` limit (`deploy/run-server.sh:47`), so the failing allocation is expected well before
  host memory runs out: `mlock(2)`, "If MCL_FUTURE has been specified, then a later system call
  (e.g., mmap(2), sbrk(2), malloc(3)), may fail if it would cause the number of locked bytes to
  exceed the permitted maximum" (https://man7.org/linux/man-pages/man2/mlock.2.html, read
  2026-09-30). A failed allocation in a `std` binary "print[s] a message to standard error and
  abort[s] the process" (https://doc.rust-lang.org/std/alloc/fn.handle_alloc_error.html, read
  2026-09-30), so the audio threads die with it. Separately,
  `set_read_timeout(10 s)` (`:545`) is per `read` call, not per request: a peer sending one byte
  every 9 s keeps its worker indefinitely, and eight such peers (the default pool, `config.rs:119`)
  make every other request a `503` (`control.rs:411-416`).
- Why it matters: K40 puts the browser path behind Traefik, but endpoints reach this port directly
  on the LAN (K40: "Endpoints use the LAN protocol directly"), so any LAN device can stop the
  control plane or the audio server; the comment claims a protection the code lacks.
- Proposed fix: read through `reader.by_ref().take(MAX_REQUEST_BYTES as u64 + 1)` for the whole
  head, reject on overflow, and enforce a whole-request deadline (for example 5 s from accept);
  add a test that sends 1 MiB with no newline and asserts 400 plus bounded RSS; suggested goal: 2.

### B-5 [MED] Every event-stream subscriber holds a control worker for its lifetime, so eight subscribers (endpoints plus UI tabs) lock out every command
- Where: `crates/server/src/control.rs:623`, `:663-705`; `crates/server/src/config.rs:119`;
  `crates/client-linux/src/control.rs:333-345`; `crates/server/src/ui/chorus.js:733`
- Evidence: `GET /api/events` runs `serve_events` on the worker that accepted it and loops until the
  peer goes (`control.rs:663-705`). Each Linux endpoint opens one (`client-linux/src/control.rs:340`),
  each open page opens one (`chorus.js:733`). The pool defaults to 8 (`config.rs:119`) and a
  connection finding no free worker gets `503` (`control.rs:411-416`). The record confirms the
  mechanism: 2 or 3 workers "cannot serve the three event streams and the commands they make"
  (`docs/verification-record.md:372`, AC-12).
- Why it matters: BRIEF §5.2 plans "a dozen unicast zones"; at seven Linux endpoints plus one open
  page, the UI's volume and mute POSTs all fail, and new endpoints cannot fetch state.

  thread population stays fixed), or reserve at least one worker for non-streaming requests and
  size the pool from the declared endpoint count; add a test with N+1 subscribers and a command;
  suggested goal: 11 (a reserved command worker is a cheap goal-2 stopgap).

### B-6 [MED] `POST /api/command` accepts any content type and checks no Origin, so any web page a LAN browser opens can change zones
- Where: `crates/server/src/control.rs:624-625`, `:459-499`
- Evidence: the route applies `request.body.trim()` whatever the `Content-Type`; `read_request`
  keeps only `Content-Length` (`:481`) and ignores every other header. A cross-site
  `fetch(url, {method: "POST", mode: "no-cors", body: "{...}"})` is sent as `text/plain`, which is a
