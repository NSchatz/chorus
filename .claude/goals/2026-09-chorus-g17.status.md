## Decisions taken

- D2 (2026-10-03): P7's condition is checked (A.2): the mDNS LEAD is not refuted, so the build
  is Option C as approved (a receiver per network namespace on macvlan), not the bridge fallback.
- D3 (2026-10-03): P7's "slot" is a "receiver" in code, flags, logs and docs, because "slot"
  already names a stream slot (`--slots`). Reasoning: `survey.md`, the naming warning.
- D4 (2026-10-03): the Soloist source is its own spelling `soloist:r<i>` (not a `player:`), so
  the overlap rules of P7 can tell it apart; stored alarm sources are `stored:<id>`, valid only
  as an alarm's source (brief 4.8: no general play-a-URL command). Reasoning: `design.md` 2.5, 3.
- D5 (2026-10-03): "a certified streamer on a line-in as an input" (§21 item 3) is read as a
  bought network streamer wired to an endpoint's line-in, modelled as a labelled input with the
  role `streamer` (autoplay on signal, a now-playing label, shareable). Nothing in the brief
  says more; the reading is recorded here and in the inputs ADR.
- D6 (2026-10-03): the homelab receivers PR stacks on PR #237's branch (the chorus-server
  compose file exists only there); the macvlan network is declared external and created by an
  owner step, so no LAN value enters a tracked file. Reasoning: `homelab.md` sections 0 and 3.5.
- D7 (2026-10-03): PR #128's `make tier-fast` was run by the coordinator (the track's own run
  waited 1800 s for `goals-heavy` and gave up: another program's heavy jobs hold two slots and
  a further slot needs headroom the loaded host does not have). The merge of main into the
  branch left conflict markers in two README files during that run; both sides were kept in the
  committed merge and `make gate-fast` re-run on it (PASS 54.1 s) under `chorus-heavy` alone,
  since the conventions checks are not a heavy job. Said in the PR body.
- D8 (2026-10-03): PR #129 (track L) landed inside PR #132's squash and was closed with a
  pointer, not merged by itself: the S2 branch contained L's branch at its merged head 1216035
  in full, its `make tier-fast` (PASS 567.9 s) ran on the tree holding both, and #129's own run
  on 1216035 waited 90 minutes for the shared heavy slot without getting it. The heavy slot is
  the day's bottleneck: I/O pressure on the host caps `goals-heavy` at one job across all
  programs (request #222 to the goals program names the part that is a tool fault: a job
  waiting on its own repo's heavy lock holds a slot). From here each track takes one lock hold
  for everything it needs.
- D1 (2026-10-03): the interactive shell's `grep` and `find` are unreliable here (§0.11); the goal
  uses `command grep` and `rg`, and `export PATH=/cache/cargo/bin:$PATH` first (g16 D11).
