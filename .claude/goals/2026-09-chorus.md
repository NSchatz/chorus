**Spec:** NSchatz/goals spec v1.1 (the `/goals:spec` skill; `spec/` at tag v1.1.0).

### 0.2 Autonomy and fallbacks

- An unsettled choice (spec `contract.md` §2) keeps, for chorus, every existing fixture, golden
  vector and test passing unless a decision retires it.
- **Research-and-propose decisions** (§5's table: P1-P10 and P14 in goal 1; P11-P13 in goals 17,
  24 and 26) are written as proposals under `docs/proposals/` (options, costs, a recommendation,
  citations). P1-P10 and P14 are decided at Checkpoint K. A later goal builds on the approved
  option; where the approval is silent, on the recommendation; where the owner **deferred** it, on
  the "If deferred" column of §5's table, and lists it under "Proposals awaiting the owner". P11-P13
  are built on their recommendation and listed the same way in that goal's report and the finale.
  Nothing proposed is ever silently final.
- **Stack changes (K95):** the owner is "not married to the tech stack". A goal may change a
  language, framework, library or the dependency posture when the scope warrants it, justified on
  fitness alone (CLAUDE.md rule 8, never on what happens to be installed) and recorded as an ADR.
  A change that is expensive to reverse is written as a proposal and listed under "Proposals
  awaiting the owner"; the goal builds on it only if the existing path cannot meet the goal.
- A finding after goal 1 that needs a decision only the owner can make takes the fallback above,
  is recorded under "Decisions taken", and is listed under "Proposals awaiting the owner".
- A rootless install (spec `contract.md` §2) includes a conda-forge environment under `/cache/opt/`
  through mise's micromamba, the way the planning research got libusb, Chromium's libraries and
  fonts. There is no `sudo`; `apt` needs root; nothing under `/etc`, `/opt` or `/usr` is edited.

### 0.3 Repos, branches, PRs

- **Branches:** `chorus-g<n>/<topic>`, one per track, from up-to-date `origin/main`.
- **Commits:** subjects `<area>: <summary>` (e.g. `protocol: ...`, `firmware: ...`), with
  `goals: ...` for ledger commits (I3); goal 3's `docs/conventions.md` may refine the style.
  Attribution follows the session's system prompt. No em dashes in messages (BRIEF §3.1).
- **Updating a PR branch:** when `origin/main` moves, merge it into the branch
  (`git merge origin/main`), never rebase a pushed branch. The squash merge keeps `main` linear.
  If `origin/main` moved only by ledger-only commits (paths under `.claude/goals/`), the last gate
  result stands; any other change means the gate runs again.
- **The merge rule:** a PR is self-merged with `gh pr merge --squash --delete-branch` only when
  the local gate passes on the branch up to date with `origin/main`, run as a heavy job (§0.4):
  `timeout 3600 "$G" lock goals-heavy -- "$G" lock -w 1800 chorus-heavy -- make tier-fast`, with its
  last 20 lines, its per-step timings and its wall-clock pasted in the PR body. **`make gate`
  recipes never take the heavy lock themselves; callers do.**
- **The gates** (`AMENDMENT-2026-10-02-goals-g9-2026-09-chorus.md`): `make tier-fast` (the
  conventions checks, fmt, clippy and the workspace tests) on every PR; `make tier-full` (= `make
  gate`) before a goal's last merge, its tail in that PR and the ledger, and nightly on main by the
  supervisor; `make gate-fast` for a docs-only or ledger-only change; `make gate` wherever a goal
  file names it.
- **CI as it really behaves:** GitHub Actions jobs do not start on this account's private repos
  (the devices, 3d and shopkit programs record it; chorus's CI last ran while the repo was public,
  2026-09-14). `.github/workflows/ci.yml` stays and calls `make gate` (K19), where steps that need
  a private input (the identity term list) print SKIPPED with the reason; read its state with
  `gh run list`, never wait on it, and never make it a merge condition. Workflow files push over
  SSH (the remote is `git@github.com:NSchatz/chorus.git`).
- **Bounded fixing:** a red gate is fixed on the branch, at most 3 fix rounds per PR. At the limit
  the track is `DROPPED (why)` in the ledger and the PR is closed with the reason and the three
  red tails, and the goal carries on, unless the track carries a line marked (foundation), in which
  case the goal ends INCOMPLETE (§0.10).
- **Batch the work:** the gate takes 10-15 minutes here, so a goal groups its work into a few
  larger PRs per track.
- **Ledger-only commits** (the goal's `.status.md`, and the checkpoint packet in goal 1) go
  straight to `main`; nothing else does.
- **Releases (K41):** goal 4 cuts `v0.1.0`; goals 5-26 may cut a minor release at their end when
  `main` is green (the ledger says whether and why); goal 27 must. A release is a `v0.x.y` tag on a
  merge commit plus a GitHub release with attached artifacts and notes that say where the source of
  every MPL-licensed dependency is (P9); pushing an image to any registry is a Needs item (§0.6).
- **Shared repos.** Lock names and order: spec `locks.md` (`shopkit-release`, then at most one of
  `shopkit-merge`, `inventory-merge`, `devices-merge` or `3d-merge`, then `goals-heavy`, then
  `chorus-heavy`). chorus has no merge lock: another program merges into chorus only between chorus's
  goals, in a drain. shopkit merges run shopkit's full `make ci` once on the branch first (it takes
  20-30 minutes here for a package add or a release, §0.11), then hold
  `"$G" lock -w 1800 shopkit-merge` only for the final `git pull --rebase`, the re-run and
  `gh pr merge`, with `timeout 3600` on the run; shopkit releases hold `shopkit-release` outside
  that (§0.13). inventory merges hold `inventory-merge` and run inventory's `make check`. homelab
  PRs are never merged by a goal.

### 0.4 Multi-agent orchestration

- The owner opted in to Workflows and subagents for parallel tracks, research and adversarial
  review (this brief and every goal file restate it).
- **At most 5 agents at once** (K29, raised 2026-09-30), and never more than
  `"$G" admit --agents <N>` allows (spec `contract.md` §4). The maker container has 28 CPUs, shared
  by its 9 Claude sessions, and the host is shared.
- **Heavy jobs** hold `goals-heavy`, then `chorus-heavy` (spec `locks.md`; §0.3 shows the command):
  `make gate` and its tiers, a cargo build or test run, an ESP-IDF build, a QEMU run, shopkit's,
  inventory's or devices' gate, a browser test, a software soak. `chorus-heavy` is exclusive, so
  chorus runs one heavy job at a time (K29); `goals-heavy`'s slots decide what runs beside other
  programs' heavy jobs. A direct `flock` call always takes `-o`, so the lock file is not inherited by
  the child. The planning research saw timing tests (`regress_0043_f1`, `control_stalled_peer`) fail
  once each while other work shared the 2 CPUs; the lock exists for that reason.
- Agents that write files work in worktrees under `/cache/wt/chorus/<repo>/<branch>`, removed
  when their PR merges or closes.
- A research claim most of its adversarial verifiers refute is dropped.
- Every agent prompt states a time budget (research 30 min, review 40 min, a build track at most 4
  hours) and tells the agent to write its output file early. A hung agent is stopped and its track
  re-run once; an agent that fails on an API rate limit is re-run once after the goal's other
  work; then the track is `DROPPED (why)`.

### 0.5 The ledger

Spec `ledger.md` applies (`.claude/goals/2026-09-chorus-g<n>.status.md`); the header also records the
goal-start SHA (§0.1), and the Baselines table each gate's wall-clock. **State words** (chorus's
dialect, I6, because K27 keeps every personal name out of tracked files): the spec's state for a step
physically impossible for an agent is written `NEEDS-OWNER (why; its issue in the owner's queue)`,
and the spec's `NEEDS-OWNER` (waiting on a request another program has not served) is written
`NEEDS-OWNER-PROGRAM (the request; workaround)`. Ledgers, goal files and reports use these words;
the other states are the spec's. An INCOMPLETE goal writes no COMPLETE line (§0.10).

### 0.7 Hardware, outward-facing limits and identity

- **Never:** flash, order, spend, or create accounts, tokens or API keys (K4); apply, deploy or
  restart anything on the homelab host (K28); touch the live Home Assistant, MQTT broker or any
  speaker. Integrations are tested against fakes.
- **Flashing and OTA guard in code:** every tool that can write to a device (flashing, an OTA push
  to a real address) refuses unless the environment variable `CHORUS_OWNER_AT_BENCH` is `1`. No
  agent command line, file, workflow or setting ever sets it. From goal 3, `make gate` runs an
  allowlist check with a fixture test of its own: every occurrence of `CHORUS_OWNER_AT_BENCH`
  outside `docs/` must be one of the approved read forms (`"${CHORUS_OWNER_AT_BENCH:-}"`,
  `env::var("CHORUS_OWNER_AT_BENCH")`, `getenv("CHORUS_OWNER_AT_BENCH")`); anything else fails.
  Owner-facing command lines that set it live only under `docs/`. Goals 9 and 14 cite the check.
  OTA installs happen only on an explicit install action (K93, I13).
- **eFuses (BRIEF §3.1 rule 2):** the firmware safety scans (no eFuse write, no Secure Boot, no
  Flash Encryption, no anti-rollback) stay in `make gate` on every target and every ESP-IDF
  version.
- **GitHub:** allowed are branches and PRs in `NSchatz/chorus` (including closing PR #18);
  `v*` tags and GitHub releases on chorus (K41); in shopkit, PRs and `v*` release tags on the release
  PR's merge commit per §0.13 (K44, I20); PRs in devices, inventory and 3d as §0.1 allows;
  never-merged PRs in homelab; issues in NSchatz/goals for the owner's queue and the requests (§0.6,
  §0.13). Goals open no issue anywhere else, never change a repo's visibility (K9), and never write
  to a public or upstream repo (K42).
- **Identity and private data (K27):** no personal name, email, LAN address, MAC address, SSID,
  account ID, API key or real hostname in any tracked file, PR body or release note. Prose says
  "the owner". The repo namespace in `NSchatz/<repo>` slugs is the one allowed form of the account
  handle (I18). The program's state name is NEEDS-OWNER (I6, §0.5). The owner's queue is only ever
  called that: its label holds a personal name, so no tracked file, PR body or release note writes
  it, and a goal reads the queue with `"$G" needs list` or `"$G" needs counts`. From goal 3, the
  identity and secret scan in `make gate` reads a private term list outside the repo
  (`/cache/chorus-private/identity-terms.txt`, I5) and fails when the list is missing (in CI it
  prints SKIPPED with the reason). In devices, the build template's own headings are devices' rule.
  Photos are never committed with EXIF or GPS.
- **Secrets:** chorus needs none of its own. The Spotify API key (K66) and any homelab credential
  stay with the owner and are reached by reference only; `gitleaks` (pinned in the repo's
  `mise.toml`) runs in the gate.

## §4 Engineering rules

### 4.1 Tests

- Fixtures, never live data, in committed tests. Hardware and services are faked: the existing
  fake amp and fake radio, a fake flash for OTA, a fake Soloist process, a scripted UPnP control
  point, a fake HA (pytest-homeassistant-custom-component or equivalent), a fake MQTT broker.
- Shared fixtures between Rust and C for protocol, sync and DSP (BRIEF §7): every file under
  `fixtures/protocol`, `fixtures/sync` and `fixtures/dsp` is read by both a Rust and a C test, and
  a check says so.
- Every calculator (DSP filters, crossovers, acoustics, loudness) is checked against a published
  worked example, cited.
- Timing tests are deterministic or carry the busy-worker refusal the repo already uses (ADR 0020).

### 4.2 Gates

- `make gate` (goal 2, K19): build, tests, firmware host checks, `verify`, determinism, `cargo fmt
  --check`, `clippy -D warnings`, the ESP-IDF compile for every approved target (K51) through
  ccache and a persistent build directory, the firmware safety scans, and from goal 3 the
  conventions checks (identity and secret scan, the `CHORUS_OWNER_AT_BENCH` allowlist, licence
  allowlist, em dashes, CLAUDE.md length, shared fixtures, measurement provenance). It prints each
  step's wall-clock. Budget 15 minutes on 2 CPUs; a goal that pushes it past 15 minutes records
  why and proposes a split (for example a slow tier run only before merges to `main`), and the
  budget is never part of a (foundation) line.
- `make gate-fast` (goal 2): the docs and conventions checks only, for ledger and docs-only
  commits.
- The web app's unit tests run without a browser; exactly one browser smoke test (install,
  service worker behind a fake login) runs in the gate (P5).

### 4.3 Conventions

`docs/conventions.md` (goal 3) is written fresh on chorus's own requirements (K18) and never cites
the retired umbrella conventions. Each rule names the check that enforces it; a check writes no
per-file record.

### 4.4 Claude Code integration

`.claude/settings.json`: `env` with the worker variables (§0.12) and `autoMemoryEnabled: false`.
No repo skills (K46). The goal files are in `.claude/goals/`.

### 4.5 Provenance

- Every measurement report names its source (`hardware`, `host`, `simulation`, `synthetic`) and a
  build commit that exists on `main`.
- Every research-backed constant cites URL and date in the comment or doc beside it.

### 4.6 Docs limits

`CLAUDE.md` <= 200 lines (K52), checked in the gate. No em dashes anywhere, checked in the gate.

### 4.7 Invariants at every merge

1. `make gate` green on the branch up to date with `origin/main`.
2. BRIEF §3.1: no GPL source or reciprocal design files read or copied (research files list what
   they read); no eFuse, Secure Boot, Flash Encryption or anti-rollback in any build (safety
   scans); no timing claim without a `docs/measurements/` report of the right source; monotonic
   clocks only in the audio path (`crates/audio-path`); no em dashes.
3. Nothing that writes to a device runs without `CHORUS_OWNER_AT_BENCH`, and the allowlist check of
   §0.7 passes in the gate.
4. The identity and secret scan is clean.
5. Every dependency's licence is on the allowlist (MIT, Apache-2.0, BSD, ISC, Zlib, public domain;
   anything else by ADR, K26, K95).

### 4.8 Security (K40, K62, K81, K92, K93)

- Volume limits enforced on the server and the endpoint for every path (I10).
- Speaker sessions encrypted; keys pinned at adoption; a changed key is refused and surfaced.
- OTA installs only images the server holds and has verified, only on the owner's command.
- Speaker microphone audio goes only to the voice path, never a shareable source (I4); the

## §33 GOAL REPORT, BLOCKED and INCOMPLETE formats

GOAL REPORT, BLOCKED and INCOMPLETE follow spec `report.md`: its headings verbatim, the lines A...
being the goal file's lettered lines. chorus's own parts follow.

**The report in chorus's words** (§0.5, K27, I6). These lines of the GOAL REPORT read as below; the
`Gate:` line follows the lettered lines (§0.10):

```
A. <line text>: DONE | NEEDS-OWNER (why; its issue in the owner's queue) | NEEDS-OWNER-PROGRAM (request; workaround) | PROPOSED (where)
Gate: <wall-clock>, per step: <timings>; past 15 minutes: <the split proposed>
Needs (this goal): <list, safety first, then what unblocks the most>
Proposals awaiting the owner: <list with paths>
Ledger: <path>@<sha>: <n> DONE, <n> NEEDS-OWNER, <n> NEEDS-OWNER-PROGRAM, <n> DROPPED (reasons listed); COMPLETE line <sha>
```

**INCOMPLETE** ends a goal only for a line marked (foundation) that cannot be met within the bound
of §0.3 (§0.10):

```
INCOMPLETE (goal <n>): a (foundation) line could not be met
line: <letter and text>
attempts: <3 fix rounds: PR URLs and the red tails>
state: <what merged, what did not>
The ledger has no COMPLETE line; goal <n+1> is BLOCKED until the owner acts.
```

**The precondition check** of goals 3-27, for the previous goal `<m>` (spec `report.md`'s ledger
check); its output goes in the BLOCKED report when it fails:

```
f=.claude/goals/2026-09-chorus-g<m>.status.md; git fetch origin \
  && git show "origin/main:$f" | rg '^COMPLETE \(goal <m>\)' \
  && ! git show "origin/main:$f" | rg -q '^\| [^|]+ \| [^|]+ \| (TODO|DOING)' \
  && echo "g<m> complete"
```
