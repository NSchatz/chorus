## Decisions taken

- 2026-09-30: the ESP-IDF pin is v6.1 itself (no v6.1.x patch exists yet); cmake 4.0.3 and ninja
  1.12.1 are installed with ESP-IDF's own `idf_tools.py` (on request in v6.1); the v5.3.6 tree
  stays for rebuilding v0.1.0. Reasoning: ADR 0042 (PR #42).
- 2026-09-30: the endpoint's crypto is Mbed TLS 4 PSA Crypto (TF-PSA-Crypto 1.1.0) from the pinned
  ESP-IDF tree on BOTH builds: the device through ESP-IDF's `mbedtls` component, the host build
  by compiling the same TF-PSA-Crypto sources, so the code held to the vectors on the host is the
  code on the chip. Not vendored separately. Reasoning: P1 (PSA Crypto on v6), ADR 0039.
- 2026-09-30: P9's libopus reaches the Linux client as the same vendored libopus source the
  endpoint compiles (through a small in-workspace sys crate), not the `opus` crate's own copy, so
  both sides run identical Opus code (P9's criterion "Same Opus code as the endpoint"); the
  codecs track records it in its ADR.
- 2026-09-30: v6.1 adds two eFuse writers (`esp_efuse_set_recovery_bootloader_offset`,
  `esp_flash_encryption_use_efuse_key`); both are now named by the image guard and the source
  scan, and every Kconfig citation of the refusal list is re-numbered for v6.1 (PR #42).
- 2026-09-30: the host build compiles TF-PSA-Crypto 1.1.0 from the pinned v6.1 tree
  (`CHORUS_IDF_V61_DIR`, refused by name when missing or at another commit) with a minimal config
  in `firmware/crypto/`; `noise.c` calls only `psa/crypto.h`. HMAC and every other PSA symbol the
  handshake needs are defined in ESP-IDF's own config (checked on the image's compile flags).
  Reasoning: ADR 0043 (PR #43).
- 2026-09-30: follow-ups from PR #43, assigned: the image keeps no key or pins across reboots
  and uses a default endpoint id until NVS storage and per-device ids land with adoption and
  provisioning (goal 14, brief section 18); the receive side's two 64 KiB static buffers are
  reviewed with the playout path (goal 8).
- 2026-09-30: operator change mid-goal (the owner asked for it): chorus#45 (cf87403) raised the
  worker variables to `CARGO_BUILD_JOBS=12`, `CMAKE_BUILD_PARALLEL_LEVEL=12`,
  `IDF_PY_BUILD_JOBS=12` and the agent cap to 5 (K29 as amended on origin/main), because chorus
  now runs in the maker container. Checked: `.claude/settings.json` on origin/main and the shell
  both print `12 12 12`. This goal's `/goal` text still says 2 and 3; the goal follows the new
  values and does not set the old ones back. One heavy job under the lock is unchanged. PR #42's
  job-cap check (ninja `-j 2` at `IDF_PY_BUILD_JOBS=2`) shows the mechanism, which is the same at
  12. PRs merged after cf87403 re-gate on a head that includes it (it changed a non-ledger file).
- 2026-09-30: PR #44's choices (ADR 0044): fixed-point libopus on both sides (S3 guidance, and
  bit-identical host and device decodes); dr_flac 0.13.3 (latest tag); Symphonia MPL-2.0 for
  four unmodified crates; the client checks FLAC CRC-16 itself (Symphonia does not); Opus mapping
  family 0 only for now; the S3 image moved to ESP-IDF's 1.5 MB single-app partition table
  (the decoders took the app past 1 MB; the OTA layout stays goal 14's). Image size on v6.1:
  923,392 to 1,062,864 bytes; DIRAM 78.19 % to 88.33 %. Host decode cost in
  `docs/measurements/codec-decode-cost-host.md` (source host, not timing evidence).
- 2026-09-30: follow-ups from PR #44, assigned to goal 8 (playout): the decode task's stack
  (libopus scratch on the caller's stack), DIRAM headroom before a jitter buffer, and a host test
  that drives a coded stream through `session.c` end to end; surround Opus (mapping family 1)
  with the theater work (goal 13).
- 2026-09-30: no minor release in goal 6: the v2 firmware makes a new key every boot until NVS
  key storage lands with adoption and provisioning (goal 14), so a released image would be
  refused by its own server after its first reboot; a release would also need `tools/release.sh`
  to carry libopus's BSD notice beside the firmware binary. The next goal whose firmware keeps
  its key is the natural point.
- 2026-09-30: tracks run as two build agents (`chorus-g6/endpoint-v2`, `chorus-g6/codecs`) plus
  the coordinator's ESP-IDF track; 3 at once at most.
